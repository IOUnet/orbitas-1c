# 1С:Предприятие — разработка расширения Orbitas

## 0. Когда применять

Используй этот скилл для любых изменений в `IOUnet/orbitas-1c`:

- расширение конфигурации 1С:Предприятие (`.cfe`);
- общие модули BSL;
- регистры сведений;
- управляемые формы и команды;
- роли и права;
- регламентные/фоновые задания;
- HTTP/JSON интеграция;
- outbox/inbox;
- миграции;
- тесты, CI/CD и сборка;
- адаптеры для БП/ERP/УТ;
- отражение подтвержденного исполнения Orbitas в учете 1С.

Перед существенным изменением сначала прочитай корневой `AGENTS.md`, затем этот файл.

Не путай расширение конфигурации с внешней обработкой (`.epf/.erf`), внешней компонентой или форком типовой конфигурации.

---

## 1. Базовые параметры проекта

Перед разработкой должны быть явно известны:

```text
base_configuration: 1С:Бухгалтерия предприятия, редакция 3.0 + точный релиз
platform_target: точная версия платформы 1С:Предприятие
compatibility_mode: режим совместимости
extension_prefix: ORB_
extension_purpose: дополнение/адаптация
interface: управляемое приложение
runtime_modes: фактически поддерживаемые
DBMS: фактически поддерживаемые
```

Если точный релиз БП или платформы неизвестен, не утверждай, что код проверен на совместимость.

Версия платформы, режим совместимости и релиз базовой конфигурации — часть контракта расширения.

---

## 2. Extension-first

Типовую конфигурацию не изменять.

Предпочтительный порядок:

1. публичный API конфигурации/БСП;
2. штатные точки расширения и переопределяемые модули;
3. подписки/события;
4. `&Перед` / `&После`;
5. `&Вместо` — только если безопасной альтернативы нет.

Не копируй большие фрагменты типового кода в расширение.

Каждый заимствованный объект должен иметь объяснение:

- зачем он нужен;
- от какого свойства/метода зависит расширение;
- что проверять после обновления БП;
- есть ли менее связанный способ.

---

## 3. Терминология 1С обязательна

В коде, документации и интерфейсе используй словарь 1С:

- Организация;
- Контрагент;
- Реализация;
- Поступление;
- Обязательство Orbitas;
- Предложение взаимозачета;
- Распоряжение на расчет;
- Состояние Orbitas;
- Отражение в учете;
- Регламентное задание;
- Регистр сведений;
- Рабочее место.

В пользовательском интерфейсе не показывать без необходимости внутренние термины Core:

- invoice graph;
- R/Q/S;
- smart-contract lock;
- on-chain settlement;
- candidate path execution.

Пользователь 1С работает с документами, обязательствами, взаимозачетом, согласованием и расчетами.

---

## 4. Граница ответственности

### 1С отвечает за

- исходные учетные данные;
- привязку Организации к Participant Passport;
- привязку Контрагента к Participant Passport;
- нормализацию документа в DTO обязательства;
- локальные binding/status projections;
- outbox/inbox;
- явное согласие пользователя;
- удобный UI;
- отражение только подтвержденного исполнения штатным способом.

### Orbitas Core отвечает за

- граф обязательств;
- поиск путей, включая открытые `A → B → C`;
- R/Q/S;
- policy/consent validation;
- locks;
- lifecycle settlement instruction;
- финальную проверку исполнения.

Не переносить clearing engine в 1С.

---

## 5. Критический инвариант учета

```text
settlement instruction != accounting settlement
```

Создание или блокировка распоряжения на расчет не означает оплату документа.

До подтвержденного `settled`:

- не закрывать взаиморасчеты;
- не менять исходный документ ради Orbitas;
- не подменять Контрагента;
- не создавать искусственную оплату;
- хранить Orbitas state отдельно от учетного состояния.

Даже после `settled` бухгалтерский эффект выполняется отдельным шагом через штатный механизм целевой конфигурации.

---

## 6. Слои

Держи явное разделение:

```text
Управляемые формы / команды
        ↓
Сценарии приложения
        ↓
Orbitas integration service
        ↓
Adapter БП 3.0 / domain mapping
        ↓
Регистры расширения
        ↓
Outbox / Inbox / фоновые задания
        ↓
HTTP / JSON transport
```

Не смешивай в одной процедуре формы:

- HTTP;
- сериализацию;
- бухгалтерскую логику;
- запись регистров;
- UI-уведомления.

---

## 7. Префикс

Все новые объекты расширения используют `ORB_`.

Не смешивать в именах объектов разные префиксы вроде `ORB_`, `Orbitas_`, `Орбитас_`.

Текстовые представления в UI могут быть русскими, технические идентификаторы — с единым префиксом.

---

## 8. Публичный API модулей

`Экспорт` — это контракт.

Для экспортного метода должны быть понятны:

- назначение;
- параметры;
- возвращаемое значение;
- ошибки;
- серверный/клиентский контекст;
- organization scope;
- идемпотентность.

Не делать методы экспортными «на всякий случай».

---

## 9. Сервер и клиент

Бизнес-логика, запросы, интеграция и запись данных — на сервере.

Клиент:

- получает компактные DTO/таблицы;
- отображает данные;
- собирает пользовательское действие;
- вызывает один осмысленный серверный сценарий.

Избегай каскада мелких клиент-серверных вызовов.

---

## 10. Запросы и производительность

Обязательные правила:

- не выполнять запрос в цикле, если можно получить данные пакетно;
- не делать N+1 чтений объектов;
- отбирать данные как можно раньше;
- не выбирать лишние поля;
- индексировать поля очереди и часто используемые ключи;
- массовые операции выполнять наборами;
- тяжелые запросы проверять на реалистичном объеме.

Для очереди отдельно проверить большой backlog.

---

## 11. Транзакции

Транзакции короткие и локальные.

```bsl
НачатьТранзакцию();
Попытка
    // только локальная работа с данными
    ЗафиксироватьТранзакцию();
Исключение
    ОтменитьТранзакцию();
    ВызватьИсключение;
КонецПопытки;
```

Запрещено выполнять внутри транзакции:

- HTTP;
- FTP;
- почту;
- blockchain RPC;
- любые потенциально долгие внешние вызовы.

---

## 12. Durable Outbox

Любой внешний write в Orbitas выполняй через устойчивую исходящую очередь.

Правильный поток:

```text
Запись локального факта / команды
        +
Запись сообщения Outbox
        ↓
COMMIT
        ↓
Регламентное задание
        ↓
HTTP Orbitas
        ↓
ответ → локальный binding/status
```

Недоступность Orbitas не должна мешать записать типовой документ 1С.

Минимальные поля outbox:

- ИдентификаторСообщения;
- Организация;
- ИсходныйДокумент;
- ТипОперации;
- ИдемпотентныйКлюч;
- ТелоJSON;
- Состояние;
- Попыток;
- СледующаяПопытка;
- ПоследняяОшибка;
- ДатаСоздания.

---

## 13. Idempotency

Любой write API обязан иметь стабильный идемпотентный ключ.

Для obligation MVP:

```text
1c:<organization_uuid>:<document_uuid>:obligation:v1
```

Retry после timeout не должен создавать дубликат.

Идемпотентность нужна и локально, и на стороне Core.

---

## 14. Retry / Dead Letter

Повторять только временные ошибки.

Использовать ограниченный exponential backoff.

После предельного числа попыток переводить сообщение в `dead`/dead-letter и показывать оператору.

Не делать бесконечный retry.

Ошибки в логах должны быть ограничены по размеру и не содержать секреты.

---

## 15. Durable Inbox

Входящие события Orbitas сначала регистрируются в inbox по уникальному `event_id`.

Повтор одного события должен быть безопасным.

Поток:

```text
Webhook/poll result
    ↓
Inbox insert-if-new
    ↓
COMMIT
    ↓
обработка
    ↓
проекция состояния / команда отражения
```

Нельзя выполнять необратимое отражение напрямую из webhook без защиты от replay.

---

## 16. HTTP

Всегда задавать timeout.

Для production HTTPS:

- проверять сертификат сервера;
- не отключать verification «для удобства»;
- не логировать Authorization/token;
- URL среды хранить в настройках Организации;
- dev/test/prod не хардкодить в бизнес-логике.

Transport не должен знать бухгалтерскую семантику.

---

## 17. Секреты

Секреты не хранить:

- в Git;
- в BSL исходниках;
- в форме в открытом виде;
- в Журнале регистрации;
- в тексте исключения.

Доступ к секретам — только серверным кодом и минимально необходимым ролям.

---

## 18. Multi-company

Все данные Orbitas scoped по Организации.

Отдельно для каждой Организации:

- Participant Passport;
- endpoint/environment;
- credentials;
- bindings;
- очередь;
- obligations cache;
- proposals;
- settlement instructions;
- policy defaults.

Credential организации A никогда не используется для B.

---

## 19. Multicurrency

Передавать раздельно:

- сумму;
- валюту документа;
- остаток;
- при необходимости сумму регламентированного учета.

Не подменять валюту документа валютой учета.

Decimal для API предпочтительно сериализовать строкой, чтобы не терять точность.

---

## 20. Stable source identity

`source_ref` должен оставаться стабильным при retry.

Идентичность должна учитывать:

- информационную базу / tenant;
- Организацию;
- тип источника;
- UUID объекта;
- сторону/транш, если один документ порождает несколько обязательств.

Не считать UUID документа глобально уникальным вне контекста ИБ/Организации.

---

## 21. Anti-corruption layer

Нельзя отдавать Core внутренние объекты 1С «как есть».

Обязательный mapping:

```text
Документ / состояние расчетов 1С
        ↓
Adapter БП 3.0
        ↓
канонический DTO Orbitas
```

Mapping должен тестироваться отдельно от HTTP.

---

## 22. Обязательство

Для каждого obligation определять:

- debtor participant;
- creditor participant;
- Organization;
- source_ref;
- source_document_type;
- original amount;
- outstanding amount;
- currency;
- due date;
- lifecycle state;
- external number/date.

Не считать универсально, что один документ 1С всегда равен одному obligation. Это правило reference adapter MVP, а не фундаментальная модель.

---

## 23. Реализация и Поступление в reference adapter

Для БП 3.0 MVP:

### Реализация
Контрагент должен Организации:

```text
debtor = Participant Passport Контрагента
creditor = Participant Passport Организации
```

### Поступление
Организация должна Контрагенту:

```text
debtor = Participant Passport Организации
creditor = Participant Passport Контрагента
```

Перед отправкой проверять наличие сопоставления Контрагента.

---

## 24. Связь Документ ↔ Obligation

Не добавлять множество Orbitas-реквизитов в типовой документ.

Использовать собственный регистр binding:

```text
Организация
ИсходныйДокумент
ObligationID
OrbitasStatus
ИсходнаяСумма
ТекущийОстаток
Валюта
ДатаОбновления
ПоследняяОшибка
```

Форма типового документа показывает projection из этого регистра.

---

## 25. Состояния обязательства

MVP должен корректно отображать как минимум:

```text
created
active
partially_settled
locked
settled
cancelled
```

Не выводить логику бухгалтерской оплаты непосредственно из этого статуса.

---

## 26. Дебиторка / кредиторка Orbitas

Рабочее место показывает:

- «Нам должны»;
- «Мы должны».

Для каждой строки:

- Контрагент;
- исходный документ;
- исходная сумма;
- текущий остаток;
- валюта;
- срок;
- состояние Orbitas;
- Obligation ID.

Источник protocol state — Orbitas; локальный регистр — кэш/projection.

---

## 27. Поиск взаимозачета

Кнопка **«Найти взаимозачет»** вызывает Core.

Ответ — только candidate paths.

1С не исполняет путь автоматически.

Для `A → B → C` показать:

- участников;
- роль нашей Организации;
- сумму и валюту;
- затронутые обязательства;
- кому предлагается направить платеж;
- меняется ли контрагент по расчету;
- срок действия предложения;
- ограничения consent/policy.

---

## 28. Consent

Approve/Reject — явные действия пользователя.

Не считать открытие формы, просмотр предложения или наличие роли оператора согласием.

Redirect на нового контрагента без approve запрещен.

Финансовое согласование требует отдельного полномочия, например:

- OrbitasRead;
- OrbitasOperator;
- OrbitasApproveSettlement;
- OrbitasAdmin.

---

## 29. Распоряжение на расчет

Хранить отдельно:

```text
SettlementInstructionID
ProposalID
ПлательщикParticipantID
ПолучательParticipantID
Сумма
Валюта
Срок
Состояние
ОтраженоВУчете
ДокументОтражения
```

Состояния:

```text
pending → locked → settled
                 ↘ expired
                 ↘ cancelled
```

`pending` и `locked` не меняют бухгалтерский учет.

---

## 30. Отражение подтвержденного исполнения

Только после повторной проверки `status = settled`.

Production adapter должен:

1. получить instruction из Core;
2. проверить Organization;
3. проверить сумму и валюту;
4. проверить исходные obligations;
5. определить уже отраженную сумму;
6. не допустить replay;
7. создать/провести штатный документ расчетов либо штатный зачет;
8. сохранить ссылку на документ отражения.

Никакой прямой записи в учетные регистры вместо штатной бизнес-операции.

---

## 31. Partial settlement

Частичное исполнение обязательно поддерживать.

Не закрывать obligation/document полностью, если подтверждена только часть.

Хранить:

- original amount;
- remote remaining amount;
- locally reflected amount;
- последнее подтвержденное состояние.

Повторный settlement event должен отражать только дельту, если модель Core это допускает.

---

## 32. Корректировки / credit notes

Корректировка долга должна быть отдельным осмысленным событием.

Не создавать новое обязательство поверх исходного автоматически, если семантика документа — уменьшение/сторнирование долга.

Mapping должен учитывать поддерживаемые документы корректировки конкретной конфигурации.

---

## 33. Проведение / отмена проведения / изменение документа

Нужно определить политику:

- документ проведен впервые;
- документ изменен после отправки;
- отменено проведение;
- пометка на удаление;
- исправлена сумма/срок/контрагент.

Не удалять историю remote obligation.

Использовать versioned upsert/cancel команду Core по контракту API.

---

## 34. Фоновые задания

Очередь обрабатывается регламентным/фоновым заданием.

Требования:

- ограниченный размер пакета;
- защита от параллельного захвата одной записи;
- timeout;
- retry/backoff;
- наблюдаемость;
- корректная остановка.

Не сканировать тяжелые учетные таблицы каждую минуту вместо работы по очереди.

---

## 35. Конкурентность

Для outbox/inbox и отражения settlement продумать atomic claim/lock.

Нельзя допускать:

- две фоновые сессии отправили одно сообщение как разные операции;
- два worker одновременно создали документ отражения;
- повтор webhook создал повторный зачет.

Используй управляемые блокировки/уникальные ключи там, где это требуется.

---

## 36. Права

Не использовать `ПолныеПрава` как рабочую роль Orbitas.

Минимум разделять:

- чтение Orbitas;
- операционные действия;
- согласование расчетов;
- администрирование подключения.

Все критические проверки прав выполнять на сервере.

UI visibility сама по себе не является защитой.

---

## 37. Привилегированный режим

Если он действительно нужен:

- ограничивать минимальным участком;
- не оборачивать целый интеграционный модуль;
- документировать причину;
- не использовать для обхода бизнес-полномочий.

---

## 38. Журналирование

Логировать:

- correlation id;
- operation type;
- source id;
- remote id;
- результат;
- класс ошибки;
- длительность.

Не логировать:

- bearer token;
- секрет;
- полный чувствительный payload без необходимости.

---

## 39. Ошибки

Не глотать исключения.

Плохой код:

```bsl
Попытка
    ...
Исключение
КонецПопытки;
```

Ошибка либо:

- корректно преобразуется в business result;
- переводит сообщение в retry/dead;
- логируется;
- пробрасывается выше.

---

## 40. Миграции

Изменение структуры собственных регистров требует versioned/idempotent migration.

Миграция должна выдерживать повторный запуск.

Не завязывать migration на ручное одноразовое действие администратора, если его можно автоматизировать безопасно.

---

## 41. Git и исходники

Source of truth — текстовые исходники и metadata source в Git.

`.cfe` — воспроизводимый release artifact, а не единственный исходник.

В PR должно быть видно, что именно изменилось.

---

## 42. Инструменты проверки

Для проекта использовать по возможности:

- 1C:EDT validation;
- «1С:Стандарты разработки V8»;
- BSL Language Server как дополнительную статическую проверку;
- YAxUnit для unit/integration;
- Vanessa Automation для критичных E2E/BDD.

Community tooling не заменяет проверку платформой/EDT.

---

## 43. Обязательная тестовая матрица Orbitas

Перед release проверить:

```text
AR export
AP export
repeat Send → no duplicate
```

## 44. Red flags — блокируют merge

PR нельзя принимать без отдельного архитектурного исключения, если есть:

- изменение типовой конфигурации;
- большой скопированный типовой метод;
- необоснованный `&Вместо`;
- HTTP внутри транзакции;
- секрет в коде/логах;
- write API без idempotency;
- retry без предела;
- отсутствие timeout;
- прямое изменение учетных регистров;
- `settlement instruction` трактуется как оплата;
- отсутствие organization scope;
- hard-coded production URL;
- отсутствие recovery для «remote succeeded / local crashed»;
- утверждение `production-ready` без реальной сборки и smoke-теста.

## 45. Mandatory Review Gate

Reviewer обязан ответить «да»:

1. Факт учета 1С отделен от protocol state Orbitas?
2. Распоряжение на расчет нигде не равно оплате до подтверждения?
3. Нет внешних вызовов внутри транзакции документа?
4. Есть стабильный idempotency key?
5. Retry после remote success не создает дубль?
6. Multi-company scope соблюден?
7. Финансовое действие требует корректных полномочий?
8. Используется штатный учетный механизм?
9. Заимствования и перехваты минимальны?
10. Есть тесты на partial/multicurrency/replay?
11. Изменение переживает обновление целевой БП?
12. Известные ограничения явно документированы?

Если хотя бы один ответ «нет», merge блокируется до исправления или принятого architectural exception.

## 46. Алгоритм агента

Перед изменением:

```text
1. Прочитать AGENTS.md и этот SKILL.md.
2. Определить точную конфигурацию/релиз/платформу.
3. Найти существующий слой и extension point.
4. Не тащить ERP-объекты в Orbitas Core contract.
5. Определить transaction boundary.
6. Для remote side effect определить idempotency/outbox/inbox.
7. Определить Organization scope.
8. Определить права.
9. Определить upgrade impact.
10. Написать/обновить тесты.
11. Только затем менять код.
```

После изменения:

```text
1. Static validation.
2. Tests.
3. Build .cfe.
4. Install in disposable exact-version IB.
5. Smoke.
6. Review borrowed objects / &Вместо / privileges.
7. Проверить replay/retry.
8. Подготовить compatibility/migration note.
```

Если текущая среда не содержит 1С:Предприятие/1C:EDT, явно сказать, какие пункты не были реально выполнены.
