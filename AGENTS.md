# AGENTS.md — Orbitas для 1С:Предприятие

## Обязательное чтение

Перед любым изменением кода, метаданных, форм, тестов или интеграционного контракта прочитай:

`.agents/skills/1c-enterprise-extension-development/SKILL.md`

Источники и ссылки к правилам находятся в:

`.agents/skills/1c-enterprise-extension-development/SOURCES.md`

Правила этого файла и SKILL.md обязательны для всего репозитория. Если локальный AGENTS.md в подкаталоге вводит более узкое правило, применяй оба; при конфликте более строгий инвариант учета/безопасности имеет приоритет.

## Назначение репозитория

Репозиторий содержит расширение конфигурации 1С:Предприятие для подключения информационной базы к Orbitas.

Пользовательский поток:

```text
Реализация / Поступление
→ Обязательство Orbitas
→ Найти взаимозачет
→ Согласовать / Отклонить
→ Распоряжение на расчет
→ Исполнение
→ Отражение в учете
```

## Целевая конфигурация MVP

Reference adapter: **1С:Бухгалтерия предприятия, редакция 3.0**.

Архитектура должна позволять позднее добавить 1С:ERP и 1С:Управление торговлей без изменения канонического Orbitas-слоя.

Точный релиз БП, версия платформы и режим совместимости должны быть зафиксированы до заявления о совместимости или production-ready.

## Терминология

Пользовательский интерфейс и документация ведутся в словаре 1С:

- Организация;
- Контрагент;
- Реализация;
- Поступление;
- Обязательство Orbitas;
- Предложение взаимозачета;
- Распоряжение на расчет;
- Состояние Orbitas;
- Отражение в учете;
- Рабочее место;
- Регистр сведений;
- Регламентное задание.

Не выносить в пользовательский интерфейс без необходимости внутренние понятия Orbitas Core: graph traversal, R/Q/S, smart-contract locks, on-chain settlement.

## Архитектурная граница

### В 1С

- исходные учетные факты;
- Participant Passport Организации;
- сопоставление Контрагент ↔ Participant Passport;
- нормализация документов в obligations;
- outbox/inbox;
- локальные projections;
- UI;
- явное согласие;
- отражение подтвержденного исполнения.

### В Orbitas Core

- граф обязательств;
- поиск candidate paths;
- открытые цепочки `A → B → C`;
- policy/consent validation;
- R/Q/S;
- locks;
- lifecycle settlement instruction;
- финальная проверка исполнения.

Не реализовывать clearing engine внутри расширения 1С.

## Обязательные инварианты

- Разработка только через расширение конфигурации; типовую конфигурацию не изменять.
- Все новые объекты расширения используют префикс `ORB_`.
- `settlement instruction != accounting settlement`.
- `pending` и `locked` не являются оплатой.
- Исходные обязательства не считаются автоматически погашенными из-за появления распоряжения на расчет.
- Redirect на нового контрагента запрещен без явного согласия уполномоченного пользователя.
- Внешний HTTP никогда не выполнять внутри транзакции записи/проведения учетного документа.
- Все внешние write-операции идут через durable outbox и стабильный idempotency key.
- Повторная доставка входящего события безопасна через inbox/replay protection.
- Настройки, сопоставления, очередь и protocol state scoped по Организации.
- Сумма и валюта передаются раздельно; валюта документа не подменяется валютой учета.
- Partial settlement и корректировки не должны переписывать историю обязательства.
- Не записывать напрямую в учетные регистры вместо штатной бизнес-операции.
- Секреты не хранятся в Git и не выводятся в лог.

## Правила разработки

Предпочтение:

1. публичный API/БСП;
2. штатные точки расширения;
3. подписки;
4. `&Перед` / `&После`;
5. `&Вместо` — только при доказанной необходимости.

Не копировать большие типовые методы.

Бизнес-логика, запросы и интеграция — на сервере. Формы должны оставаться тонкими.

## Надежность интеграции

Любая операция, создающая remote side effect, должна отвечать на вопросы:

- какой idempotency key;
- где outbox;
- как обрабатывается timeout;
- как обрабатывается «remote succeeded / local crashed»;
- сколько retry;
- когда dead-letter;
- как выполняется reconciliation;
- как предотвращается replay.

Если ответов нет — реализация не готова к merge.

## Бухгалтерское отражение

После подтвержденного `settled`:

1. повторно проверить instruction в Orbitas Core;
2. проверить Организацию, сумму, валюту и исходные obligations;
3. проверить уже отраженную сумму;
4. выполнить штатный механизм учета конкретной конфигурации;
5. сохранить ссылку на документ отражения;
6. обеспечить идемпотентность и partial settlement.

Никогда не считать protocol state заменой бухгалтерского факта.

## Перед merge

Обязательны:

- static validation;
- тесты mapping/idempotency/replay;
- multi-company;
- multicurrency;
- partial settlement;
- проверка прав;
- проверка отсутствия HTTP в транзакции;
- compatibility note по базовой конфигурации.

Если среда не содержит 1С:Предприятие/1C:EDT, не утверждать, что `.cfe` собран или проверен. Явно перечислить непроверенные пункты.
